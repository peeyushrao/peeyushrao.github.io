## What information should be gathered before escalating an alert?

Before escalating an alert, an analyst should gather **sufficient context** to determine whether the alert is a **true positive or false positive**, understand its **potential business impact**, and assess the **scope of activity**. Escalation should occur only after a preliminary investigation has converted a raw signal into an **actionable incident**.

---

## 1. Primary System and Host Information

The first step is establishing the **who** and **where** of the alert.

### Host Details
- Hostname
- IP address
- Operating system and version

### Asset Criticality
- Is the host a high‑value target?
  - Domain controller
  - Production server
  - System handling sensitive data (PII, financial records)

### System State
- System uptime
- Current resource utilization

This helps distinguish system issues from active attacks.

---

## 2. Process and Execution Context

Understanding what code is executing is essential for identifying malicious intent.

### Process Information
- Process name
- Process ID (PID)
- Parent process

### Command Line Arguments
- Full command line used for execution
- Indicators of living‑off‑the‑land abuse (e.g., PowerShell, CMD, MSHTA)

### File Integrity
- File path
- Hashes (MD5, SHA‑256)
- File creation and modification times

---

## 3. User Activity and Authentication

Attackers frequently abuse valid credentials, making user context critical.

### Account Details
- Username and domain
- Privilege level (standard user, administrator, service account)

### Login Patterns
- Multiple failed login attempts
- Unusual login times
- Logins from unfamiliar geographic locations

### Session Tracking
- Correlate activity using the Logon ID
- Identify all actions performed during the same session

---

## 4. Network and Communication Data

Network telemetry provides evidence of command‑and‑control (C2) or data exfiltration.

### Connection Metadata
- Source IP
- Destination IP
- Destination port

### Traffic Volume
- Sudden spikes in outbound data (possible exfiltration)
- Unexpected inbound traffic (payload delivery)

### Protocol Anomalies
- Non‑standard protocols over common ports (e.g., HTTPS abuse on port 443)
- Indicators of DNS tunneling or beaconing behavior

---

## 5. External Threat Intelligence

Validating internal findings against external intelligence improves confidence.

### Reputation Checks
- IP addresses
- Domains
- File hashes

### Attacker TTP Mapping
- Match observed behavior to known Tactics, Techniques, and Procedures (TTPs)
- Identify the attacker’s stage in the kill chain

---

## CrowdStrike Falcon Escalation Context

In **CrowdStrike Falcon**, escalation‑ready context typically includes the following dimensions.

---

## 1. Process Context

- Process name and path
- Command line
- Parent and grandparent processes
- Execution location (e.g., `System32` vs user‑writable paths)

**Falcon Data Sources:**
- `ProcessRollup2`
- Process Tree

---

## 2. User and Identity Context

- Logged‑in user
- Privilege level (standard user, admin, service account)
- Interactive vs non‑interactive session

Escalation urgency changes immediately if a **privileged account** is involved.

---

## 3. Host Context

- Host role (workstation, server, domain controller)
- Business criticality
- Internet‑facing status
- Previous detections on the same host

**Falcon Views:**
- Host Summary
- Host Timeline

---

## 4. Behavioral Sequence (Before and After)

Escalation should be driven by **behavior chains**, not isolated events.

### Key Questions
- What happened before the alert?
- What happened after the alert?

### Indicators to Review
- Network connections
- Credential access attempts
- Child process creation
- Persistence mechanisms

---

## 5. Rarity and Baseline

- First‑seen behavior?
- Rare process or DLL in the environment?
- Normal for this user or host?

Falcon’s historical and fleet‑wide baseline is critical for this assessment.

---

## 6. Scope Indicators

Determine whether activity is isolated or widespread.

- Same behavior on other hosts
- Same user across multiple systems
- Same hash or command observed elsewhere

---

## Key Takeaway

Alerts should be escalated **only when context confirms risk**.

- Events are signals
- Context reveals intent
- Behavior chains justify escalation

A mature SOC escalates **incidents**, not alerts.
