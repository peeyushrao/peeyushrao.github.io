What information should be gathered before escalating an alert?

Before escalating an alert, an analyst should gather comprehensive
contextual information to determine the alert\'s accuracy (True Positive
vs False Positive), its potential impact on business operations, and the
overall scope of the activity. Escalation should only occur after a
preliminary investigation has transformed a raw signal into an
actionable incident.

1\. Primary System and Host Information - The first step is to identify
the \"who\" and \"where\" of the alert to establish the environmental
context.

> • Host Details: Gather the hostname, IP address, and the specific
> operating system version.
>
> • Asset Criticality: Determine if the host is a high-value target,
> such as a domain controller or a server containing sensitive data
> (e.g., PII or financial records).
>
> • System State: Check the system uptime and current resource
> utilisation to see if the alert is related to a system performance
> issue or an actual attack.

2\. Process and Execution Context - Understanding what code is running
is vital for identifying malicious intent.

> • Process Information: Identify the New Process Name, its Process ID
> (PID), and its Parent Process.
>
> • Command Line Arguments: Review the full command line used to launch
> the process to see if legitimate system utilities (e.g., PowerShell or
> CMD) are being misused.
>
> • File Integrity: Check for suspicious files, their hashes
> (MD5/SHA256), and their creation/modification times (mtime).

3\. User Activity and Authentication - Adversaries often use valid
credentials to move laterally, making user context a high priority.

> • Account Details: Identify the username and domain involved and check
> their assigned privilege levels (e.g., administrative vs standard
> user).
>
> • Login Patterns: Look for unusual login behavior, such as multiple
> failed attempts, logins from unfamiliar geographic locations, or
> access at odd hours.
>
> • Session Tracking: Use the Logon ID to correlate all activities
> performed by that specific user during the session in question.

4\. Network and Communication Data - Network telemetry provides evidence
of command-and-control (C2) or data exfiltration.

> • Connection Metadata: Gather the Source IP, Destination IP, and
> Destination Port.
>
> • Traffic Volume: Check for sudden spikes in transferred bytes
> (outbound) or received bytes (inbound) which may indicate exfiltration
> or malware downloads.
>
> • Protocol Anomalies: Inspect for non-standard protocols running over
> common ports (e.g., unusual traffic over port 443) or evidence of DNS
> tunnelling.

5\. External Threat Intelligence - Cross-referencing internal data with
external intelligence confirms if the artifacts are known threats.

> • Reputation Checks: Query the reputation of involved IP addresses,
> domains, and file hashes against threat intelligence platforms.
>
> • Attacker TTPs: Match the observed behavior against known Tactics,
> Techniques, and Procedures to identify which stage of the attack
> lifecycle the adversary has reached.

In CrowdStrike Falcon, escalation-ready context typically includes:

1\. Process Context -

- Process name and path

- Command line

- Parent and grandparent processes

- Execution location (System32 vs user-writable path)\
  Example Falcon data: ProcessRollup2, Process Tree

2\. User & Identity Context

- Logged-in user

- Privilege level (standard user, admin, service account)

- Interactive vs non-interactive session

- Escalation changes immediately if a privileged account is involved.

3\. Host Context

- Host role (server, workstation, DC)

- Business criticality

- Is the host internet-facing?

- Previous detections on the same host\
  Falcon Host Summary + Host Timeline

4\. Behavioral Sequence (Before & After)

- What happened before the alert?

- What happened after the alert?

  - Network connections

  - Credential access attempts

  - Child processes

  - Persistence indicators

**Escalation is justified when behavior chains, not when events are
isolated.**

5\. Rarity & Baseline

- First-seen behavior?

- Rare process/DLL in the environment?

- Normal for this user/host or not?

Falcon's historical and fleet-wide context matters here.

6\. Scope Indicators

- Same behavior on other hosts?

- Same user across hosts?

- Same hash or command observed elsewhere?
