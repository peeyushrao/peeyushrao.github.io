### What is a false positive and how do you confirm one? 

A false positive is an alert that incorrectly identifies benign or
authorised activity as a malicious threat. This occurs when security
tools, such as an Intrusion Detection System (IDS) or SIEM, flag
activity that matches a signature or rule but lacks actual malicious
intent. These alerts are a significant operational burden because they
consume limited time and resources that should be spent on genuine
incidents.

How to Confirm a False Positive - Confirming that an alert is a false
positive requires a systematic validation process:

> • Analyse Context and Severity: Review the alert metadata to see if
> the activity aligns with known organised activity, such as routine
> server backups, software updates, or scheduled administrative tasks.
>
> • Stakeholder Communication: Consult with relevant departments (e.g.,
> network or system administration teams) to determine if a specific
> data transfer or configuration change was authorised.
>
> • Threat Intelligence Cross-Referencing: Check the reputation of
> involved artifacts, such as file hashes, IP addresses, or URLs,
> against threat intelligence platforms. If multiple engines flag an
> artifact as \"clean\" or \"trusted,\" the alert is likely an error.
>
> • Behavioural Analysis (Sandboxing): For suspicious files or scripts,
> execute them in an isolated sandbox environment to observe their
> actual behaviour. If the code does not perform malicious actions like
> establishing persistence or exfiltrating data, it may be a false
> positive.
>
> • Frequency Analysis (Stacking): Determine if the \"suspicious\"
> activity is rare or common across the environment. If a specific
> process is running on 1,000 identical workstations, it is likely part
> of a standard \"gold build\" rather than a unique infection.

In other words, A false positive is a detection that correctly
identifies suspicious behavior but incorrectly classifies it as
malicious, when it is actually legitimate activity. You confirm a false
positive by validating intent and legitimacy through context, not by
assuming benign behavior based on familiarity or severity.

A detection is only a false positive after investigation, never by
default.

In CrowdStrike Falcon, confirming a false positive is a structured
investigation, not a quick dismissal.\
\
Step 1: Validate the Behavior (Not the Tool)

- Review Process Tree

- Check command line

- Identify parent process

- Look for behavior chaining

Step 2: Validate the User & Host Context

- Who executed it?

  - Standard user vs admin vs service account

- Where did it run?

  - Finance workstation vs IT admin server

- Is this expected for this user on this host?

Falcon Host Summary + User context is critical here.

Step 3: Check Historical Baseline

- Has this behavior occurred before?

- Is it common across the environment?

- Is this a first-seen event?

Falcon's historical telemetry often decides FP vs TP.

Step 4: Look for "After-Effects"

A true false positive usually has no follow-on activity:

- No network beaconing

- No credential access attempts

- No persistence mechanisms

- No lateral movement

Malicious intent reveals itself after execution.

Step 5: Validate the Business Use Case

- Is the tool approved?

- Is the command consistent with documented admin workflows?

- Confirm with IT only after technical validation

Never accept "IT does this" without evidence.
