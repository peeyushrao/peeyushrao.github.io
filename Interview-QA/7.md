## What is a false positive and how do you confirm one?

A **false positive** is an alert or detection that incorrectly identifies **benign or authorized activity** as malicious. This typically occurs when security tools such as IDS, EDR, or SIEM platforms flag activity that matches a rule, signature, or analytic pattern but **lacks malicious intent**.

False positives are a major operational burden because they consume analyst time and resources that should be focused on **true incidents**.

---

## What a False Positive Is — and Is Not

- A false positive is a **detection that looks suspicious** but is ultimately **legitimate activity**
- A detection is **never a false positive by default**
- A detection becomes a false positive **only after investigation**

You confirm a false positive by validating **intent and legitimacy through context**, not by assuming safety based on familiarity or severity.

---

## How to Confirm a False Positive

Confirming a false positive requires a **systematic validation process**, not a quick dismissal.

---

## 1. Analyze Context and Severity

- Review alert metadata and triggering logic
- Determine whether activity aligns with:
  - Scheduled backups
  - Software updates
  - Administrative scripts
  - Approved automation

Severity alone is insufficient—context determines meaning.

---

## 2. Stakeholder Communication

- Consult relevant teams (IT, network, system administrators)
- Validate whether:
  - The activity was authorized
  - The timing matches planned changes

Stakeholder confirmation supports—but does not replace—technical validation.

---

## 3. Threat Intelligence Cross-Referencing

- Check reputation of involved artifacts:
  - File hashes
  - IP addresses
  - Domains and URLs

If multiple reputable intelligence sources classify artifacts as clean or trusted, the alert is **more likely** a false positive.

---

## 4. Behavioral Analysis (Sandboxing)

- Execute suspicious files or scripts in an isolated sandbox
- Observe runtime behavior

Indicators of malicious intent include:
- Persistence mechanisms
- Credential access
- Lateral movement
- Data exfiltration

Absence of these behaviors supports a false positive determination.

---

## 5. Frequency Analysis (Stacking)

- Determine how common the behavior is across the environment
- If the same process runs on hundreds or thousands of identical systems, it may be part of a **standard gold build**

Rare behavior is suspicious; common behavior is often legitimate.

## CrowdStrike Falcon Perspective

In **CrowdStrike Falcon**, confirming a false positive is a **structured investigation**, not a quick dismissal.

---

## Step 1: Validate the Behavior (Not the Tool)

- Review the process tree
- Inspect the full command line
- Identify parent and grandparent processes
- Look for behavior chaining across detections

---

## Step 2: Validate User and Host Context

- **Who executed it?**
  - Standard user
  - Administrator
  - Service account
- **Where did it run?**
  - Finance workstation
  - IT admin server
- **Is this expected for this user on this host?**

Falcon Host Summary and user context are critical here.

---

## Step 3: Check Historical Baseline

- Has this behavior occurred before?
- Is it common across the environment?
- Is this a first-seen event?

Falcon’s historical telemetry often determines **false positive vs true positive**.

---

## Step 4: Look for After-Effects

True false positives usually have **no follow-on activity**.

Indicators typically absent in false positives:
- Network beaconing
- Credential access attempts
- Persistence mechanisms
- Lateral movement

Malicious intent usually reveals itself **after execution**.

---

## Step 5: Validate the Business Use Case

- Is the tool approved?
- Is the command consistent with documented administrative workflows?
- Confirm with IT **only after** technical validation

> Never accept “IT does this” without evidence.

---

## Key Takeaway

- False positives are identified **through investigation**, not assumption
- Context, behavior, and baseline matter more than alert labels

A mature SOC confirms false positives carefully—protecting analysts from noise **without blinding the organization to real threats**.
